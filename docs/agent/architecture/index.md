# Architecture

MyGitNotes is structured as a TypeScript monorepo using pnpm workspaces.

## Monorepo Layout

- `packages/core`: Core domain models, `.mygitnotes.yaml` (or the compatible `.github-notes.yaml`) schema & parsing, Markdown & YAML frontmatter parsing with exact round-trip preservation, resource classification, and path traversal guards.
- `packages/git`: Guarded Git service operations, Core update engine, and semantic commit message generation (with Gemini Flash-Lite and deterministic fallback).
- `packages/mcp-server`: Stdio Model Context Protocol (MCP) server providing safe note, asset, git, and workspace operations to coding agents.
- `apps/local-server`: Lightweight local HTTP bridge serving workspace APIs and static assets to the frontend web application.
- `apps/web`: Responsive, modern React frontend supporting List, Card, and Kanban views, pure Markdown & plain-text editors, asset manager, and crash-recovery drafts.
- `scripts/`: Cross-platform Node/TypeScript scripts for `bootstrap-workspace`, `update-core`, `migrate-workspace` and `convert-workspace`.

## Core Invariants

1. **Markdown is the source of truth**: Notes are plain Markdown files with optional YAML frontmatter. No proprietary database or HTML blob becomes authoritative over files on disk.
2. **Boundary between Core and User content**: `core` carries only product source and `main` carries only workspace content (`.mygitnotes.yaml`, notebook roots, assets, workspace Agent settings). The local server runs from a `core` worktree and edits the `main` worktree named by `MYGITNOTES_LOCAL_PATH`; `core` only fast-forwards and never merges into a content-only `main`. Fork-model workspaces whose `main` still carries the product merge Core with workspace Agent paths restored until they run `convert-workspace`.
3. **Round-trip fidelity**: Updating a note's frontmatter (e.g. changing Kanban column/status) preserves all unknown frontmatter fields and the original markdown text unchanged.

## Configurable sources

`mygitnotes.server.yaml` (or the compatible `github-notes.server.yaml`) selects a local repository, GitHub repository or GitLab project. Without a configured local path, a local source reads the application root only when it holds a workspace manifest (fork model); otherwise startup fails and names `bootstrap-workspace`. Local startup also rejects a workspace whose `schema_version` differs from `SUPPORTED_SCHEMA_VERSION` (now 3, compilations); `migrate-workspace` upgrades it, converting Screen lanes into `*.compilation.yml` files. Compilations are note-shaped files served through the note routes; there is no `/api/screen-page`. Product reference documents under `docs/agent/**` are served read-only from the application root, not from the workspace. Source configuration accepts `MYGITNOTES_*` and legacy `GITHUB_NOTES_*` environment variables.

The deployment's source is the home repository, which holds the workspace manifest. A notebook may declare `source` to live in its own notebook repository (manifest `schema_version: 2`). Every request resolves its configuration through the replaceable `WorkspaceConfigSource` and its repositories through `WorkspaceRepositories`, which opens each notebook repository with the signed-in credential (hosted) or the worktree mapped under `repositories` in `mygitnotes.server.yaml` (local), and reports unreachable ones as unavailable. Revisions, drafts, commits, compilation/Focus/Study files, Agent files and Git status are per repository; one write never spans repositories. See [ADR 0001](../../adr/0001-multi-repository-notebooks.md).

`RemoteSource` contains shared note, folder, asset, compilation and Study rules. `GitHubSource` and `GitLabSource` implement immutable reads and atomic commits. `createRemoteSource` selects the adapter for HTTP and remote MCP. GitLab supports an HTTPS base URL and nested project namespaces.

OAuth follows the selected provider. Encrypted server records isolate site and account identity. GitLab refresh tokens are rotated under a credential lock and shared by browser sessions and persistent MCP grants. GitHub keeps its existing credential and grant identifiers; short-lived GitHub OAuth app tokens rotate under the same credential lock for persistent MCP grants, while GitHub browser sessions end with their access token.

See the [deployment guide](../../deploy.md).

## Editions and extension points

This repository is the AGPL-3.0 community edition; the private Pro edition includes it as a Git submodule and composes it without editing it ([ADR 0002](../../adr/0002-open-core-editions.md)). The server's composition root is `createApp(base, services)`: an edition may supply the `configSource`, `recordStore`, `sessions`, `workspaceChoices`, `remoteCache`, `piAgent`, the `assetStorage` (which R2 bucket and key prefix each request reaches, with optional `reserve(scope, key, bytes)` and `record(scope, key, deltaBytes)` quota hooks; a non-empty prefix must end in `/`; `envAssetStorage` is the default), the `webDist` it serves, and a `routes` hook mounted after sign-in and before the workspace routes. `@mygitnotes/local-server` resolves to `src/edition.ts`, which starts nothing, and `@mygitnotes/local-server/testing/record-store-contract` and `…/testing/workspace-choices-contract` are the behavior every record store and every workspace choice store must keep; `…/testing/asset-storage-contract` does the same for an `AssetStorage`. Every R2 route, the asset handler and the MCP asset tools (`list_assets`, `add_asset`, `delete_asset`, local and remote) read keys through the scope: a key outside the scope's prefix is not found, and MCP uploads are reserved and recorded like the browser's. The `/mcp` body limit is decided after sign-in from the scope too (64 MiB when the storage has a bucket for the caller, else 8 MiB). An upload URL signs the declared `Content-Length`, and `reserve` names the key so an edition can hold a pending row for an upload the browser never confirms; the browser reports the finished upload at `/api/r2/uploaded`, which confirms the key (idempotent: it may repeat, so an edition keeps one row per key) and is when `record` runs, and answers at once without a bucket or GitHub request when the storage has no `record`. A `PiAgent` (`router`, optional `upgrade`) is mounted at `/api/pi` in remote mode too, which stays empty for the community edition because it passes none; the web app asks a remote deployment for an agent session only when a `WebFeature` sets `agent: true`. An agent session starts in an agent workspace, `{ repository, folder }` (folder empty for the repository root; see [agent workspaces](../workflows/workspace-agent-system.md)), and `PiSessionInfo.location` reports it. `createPiAgent({ webTools: true })` gives Pi note tools that edit the working changes of the page holding the panel instead of files (see [web agent tools](../mcp/index.md#web-agent-tools)); `PiSession` and `WebToolError` are exported for an edition that runs its own bridge. Browser working changes include deletions (`WorkingNote.deleted`), listed in the Changes tool's uncommitted trash and committed through `/api/notes/commit` as `{ path, delete: true }`, which removes the note's version file in the same commit. A `PiAgent` may leave out `upgrade`, and a `PiSessionInfo.socket` (`{ url, protocols? }`) makes the web panel connect there instead of to `/api/pi/ws` on its own host. The web app's entry is `createWebApp(root, { features })` (`@mygitnotes/web`); a `WebFeature` (`@mygitnotes/web/features`) may add top-level routes, Settings sections, entries in the signed-in account menu (`accountMenuItems`) and Agents-page sections for the selected agent workspace (`agentWorkspaceSections`, given `{ repository, folder }`; the community edition has none; Pro plans to put its MCP server settings there), or replace the header's account controls, supply `agentModelSetup` (shown in the agent panel in place of the message box while Pi answers `get_available_models` with no model, with a button that asks again; without it the panel explains how to add a provider key to Pi), supply `commitMessagePolish` (an "AI polish" button in the commit dialog of a remote workspace only, because the local commit path has no generated details; the `Note-Added`, `Note-Modified` and `Document-Modified` trailers are always written again from the facts, and a body too long for the 4,000-character message limit is cut, never the trailers) and `gate` (whether the agent panel, the R2 panel and the polish button, named by `FEATURE_IDS`, are open to the user, with a reason shown in place when not; presentation only); `@mygitnotes/web/kit` exports the components and hooks an edition builds those from (`Button`, `LoadingStatus`, `Select`, `useTranslation`). A store that does not outlive the process reports `durable: false`, and the agent grant routes then answer 404. A store missing configuration it needs reports `ready: false` (the community store on Vercel without Redis), and `/api/auth/session` then answers `configured: false`; an edition's own store leaves `ready` unset.

Browser sign-ins go through `BrowserSessions` (`apps/local-server/src/browser-sessions.ts`): `storedSessions` keeps an opaque cookie id over the record store, and `cookieSessions`, the lightweight mode chosen by `storageMode()` (`MYGITNOTES_STORAGE=cookie`, or Vercel without Redis), seals the session into the cookie and pairs with `NoRecordStore`. `authToken(req, res, …)` refreshes a cookie session's GitHub App token and writes the rotated session back; `/api/auth/session` refreshes ten minutes ahead, and the web app's `WorkspaceGate` awaits it before the workspace loads. A GitHub deployment without `MYGITNOTES_REPOSITORY` lets each visitor choose: `chosenRepositorySource` serves the repository `WorkspaceChoices` reads for the request (the community `cookieWorkspaceChoices` seals it into the visitor's `mygitnotes_workspace` cookie and forgets it on sign-out) or raises `WorkspaceSetupError` with `reason: 'choose-repository'`, and `/api/repositories/available` and `/api/workspace/choice` list and set it. The list answer carries `newRepositoryUrl`, GitHub's new-repository page prefilled with the starter template (`MYGITNOTES_STARTER_TEMPLATE`, default `wayne930242/mygitnotes-starter`); the picker selects the repository that appears when the visitor returns. A home repository without a manifest gets one derived from its top-level Markdown folders (`deriveWorkspaceConfig`); `/api/workspace` reports `manifest: 'derived'`, and saving the manifest creates `.mygitnotes.yaml`. Missing seams are added here first, with community behavior unchanged.

## Self-hosted runtime

The [Dockerfile](../../../Dockerfile) builds the web application and runs the compiled Express server as the `node` user. `HOST` defaults to loopback for direct startup and is set to `0.0.0.0` inside the image. The local-source Host and Origin checks remain active; `compose.local.yaml` binds an existing workspace checkout at `/workspace` and publishes only a loopback port.

Note pages come from query routes shared by both sources: `/api/notes/query` (notebook, folder, tag, status, visibility, text and sort filters, cursor pages, optional content, or a full path list), `/api/notes/facets`, `/api/notes/lookup`, `/api/notes/agenda` and `/api/notes/graph`. `NoteCatalog` is the read model behind them: `workspaceCatalog` joins one `RepositoryCatalog` per repository of the request's workspace. `parseNoteQuery` and the query functions live in `packages/core/src/note-catalog.ts`, and filtering, sorting and serialization are shared with the browser through `note-query.ts`. Read routes accept the `revisions` the browser is working from (a JSON `RevisionSet`, one commit per repository) and answer 409 with `staleRepositories` when a branch head has moved (a mismatch with the cached head is rechecked against the uncached head first, since another server instance may have committed), so a screen never mixes two commits of one repository and a request cannot steer reads at arbitrary history. Answers carry the `revisions` of the repositories they read. A note is identified by its notebook and path (`NoteRef`, keyed by `noteRefKey`): `/api/notes/lookup` takes `notes: NoteRef[]`, path selection answers `notes: NoteRef[]`, and browser drafts are keyed the same way, so equal paths in two repositories stay distinct.

Remote readers cache notes and their per-notebook indexes in the session Redis, keyed by repository and Git object id with a 30 day lifetime, falling back to a process-local cache when Redis is absent. Cache failures end the request rather than silently reloading from the platform.

`compose.yaml` runs the remote-source application with its own Redis service on an internal network. Redis persists AOF data in `redis-data`; only the application HTTP port is published. Encrypted records go through a `RecordStore` (`apps/local-server/src/record-store/`): `SealedRecordStore` seals values, expires them, lists grants and orders credential locks over a raw `RecordBackend`. `createRecordStore` chooses native Redis via `REDIS_URL`, then the existing Redis REST configuration, then a local encrypted session directory outside Vercel. Native Redis reuses connections, bounds connection/command waits, and propagates errors; a later request reconnects after a failure. Session/grant keys, encryption, TTLs, indexes, and credential refresh locks use the same operations across both Redis transports.

See the [deployment guide](../../deploy.md#docker-compose-with-a-remote-repository) for volumes, OAuth callbacks, reverse proxies, and updates.

## Notebook statuses and visibility

Each manifest notebook accepts an optional ordered `statuses` array, for example
`statuses: [capture, review, published]`. Missing or empty definitions fall back to
`inbox`, `working`, `done`, `archived`. The first entry is the initial status for
new notes; the order also determines Kanban columns. Update definitions through
the local Settings manifest editor or the source repository manifest.

The browser-safe core note-status module combines definitions with observed note
values. Unknown values extend choices for that notebook; definitions remain
unchanged. Values are case-sensitive and retain their original spelling. Existing
notes retain all metadata, and unassigned notes remain without a status.

The note YAML boolean `hiden` controls visibility. When absent, archived notes
are hidden and other notes are visible. An explicit false keeps even an archived
note visible. UI archive actions set hiden to true; leaving archived sets it to
false. Other status changes preserve manual visibility. The metadata editor also
exposes Hide note. Sidebar Show hidden notes includes hidden notes in List, Card,
Kanban and search, with the choice stored in the showHidden URL query. Direct
note links, repository reads and MCP access still resolve hidden notes. Visibility
is a presentation preference, not an authorization boundary.
